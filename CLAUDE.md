# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

OpenAPI::Client::OpenAI is a Perl client for the OpenAI API, built on top of OpenAPI::Client (which uses Mojolicious). It auto-generates API methods from an OpenAPI specification YAML file (`share/openapi.yaml`). The module is distributed on CPAN.

## Build & Test Commands

```bash
# Initial setup / rebuild after changes
perl Makefile.PL && make

# Run all tests (t/ and devel/t/; most t/ tests need OPENAI_API_KEY)
make test

# Run a single test
prove -lv t/create_chat_completion.t
prove -lv devel/t/docgen-render-path.t

# Run tests with release testing enabled (adds POD, POD-coverage, MANIFEST checks)
RELEASE_TESTING=1 make test

# Full rebuild (cleans, rebuilds, regenerates docs + MANIFEST + README, runs tests)
devel/rebuild

# Rebuild with updated OpenAPI spec from upstream
devel/rebuild --update

# Rebuild without running tests
devel/rebuild --notest

# Clean build artifacts
make realclean
```

### Regenerating documentation

**Use `devel/rebuild`.** It is the only supported way to regenerate the docs, and
the only sequence that gets the ordering right: `make realclean` → build →
`devel/build_docs.pl` → `make manifest` → `pod2markdown`.

`make manifest` rewrites MANIFEST from whatever is in the working tree, filtered
by `MANIFEST.SKIP`. Build artifacts are covered (`blib/`, `pm_to_blib`) — commit
`30da29a` ("Fix bad MANIFEST") added those patterns after 221 `blib/` entries got
swept in. Anything untracked and *unskipped* still lands in MANIFEST and then in
the next tarball. A `make dist` tarball sitting in the working directory is the
common case; run `make clean` before regenerating docs.

Skipping the MANIFEST refresh is the opposite failure and is just as real: a spec
update that adds endpoints produces new `lib/OpenAPI/Client/OpenAI/Path/*.pod`
files, and files absent from MANIFEST are absent from the distribution tarball
while `Path.pod` still links to them. Nothing routinely catches this — CI's
`make distcheck` warns but exits 0, and `t/manifest.t` only checks under
`RELEASE_TESTING`. It happened once for five months across the 0.25 release
(38 files, commits `0c6dcbc` → `120d24b`).

## Architecture

### Modules

`lib/OpenAPI/Client/OpenAI.pm` — the class users instantiate. Subclasses
`OpenAPI::Client` (Mojo::Base). The constructor:
- Requires `OPENAI_API_KEY` environment variable
- Loads `share/openapi.yaml` as the API specification
- Sets up Bearer token auth via Mojo UA hooks
- Registers a `file_upload` transactor generator for file upload endpoints (e.g., transcription)

At module load it installs a snake_case alias for **every** operationId in the
spec. Both forms are first-class — `create_chat_completion` and
`createChatCompletion` are equally supported, and neither is deprecated.
Installation **croaks at load time** if two operationIds collapse to the same
snake_case name, which an upstream spec update can introduce; see
`t/alias_collision.t` and the fixture `t/fixtures/colliding-spec.yaml`.

`lib/OpenAPI/Client/OpenAI/Naming.pm` — `to_snake_case` and `detect_collisions`,
exported on request. Separate and installed (not inlined) because the doc
generator under `devel/lib/.../DocGen/Render/` imports the same functions, and
`devel/` is excluded from the dist — one conversion, so runtime aliases and
generated POD cannot drift. Tested by `t/naming.t`.

All API methods (e.g., `createChatCompletion`, `listModels`) are auto-generated by OpenAPI::Client from the spec — they are not defined in the Perl source.

### OpenAPI Specification

`share/openapi.yaml` — The OpenAI OpenAPI spec, installed via File::ShareDir. This is the single source of truth for all available API endpoints. Updated from upstream via `devel/rebuild --update` (fetches from Stainless API).

### Doc Generator

`devel/build_docs.pl` is a thin CLI wrapper — it reads two optional `@ARGV`
values, constructs `OpenAPI::Client::OpenAI::DocGen`, and calls `->run`. It
parses nothing.

The generator itself lives in `devel/lib/OpenAPI/Client/OpenAI/DocGen/`:

- `DocGen.pm` — orchestrator; walks the spec's paths and writes each output file
- `Spec.pm` — YAML loader with non-inlining `$ref` resolution
- `Schema.pm` — walks schemas into property records
- `Example.pm` — synthesizes example values (priority rules, `oneOf` scoring, cycle detection)
- `Markdown.pm` — Markdown → POD conversion for spec descriptions
- `Render/Path.pm`, `Render/PathIndex.pm`, `Render/MethodIndex.pm` — the POD emitters

`devel/lib/` and `devel/t/` are excluded from the distribution but `devel/t/*.t`
**is** wired into `make test` (see `Makefile.PL`'s `test` key). Any change to
DocGen must be validated with those tests, including
`devel/t/docgen-integration.t` and the `devel/t/podcheck-baseline.txt` baseline.

Note: `DocGen.pm` writes every path unconditionally but never deletes. A POD file
for an endpoint the upstream spec has dropped will linger until removed by hand.

### Generated Documentation

`devel/build_docs.pl` generates:
- `lib/OpenAPI/Client/OpenAI/Path.pod` — Index of all API paths
- `lib/OpenAPI/Client/OpenAI/Path/*.pod` — Per-endpoint documentation
- `lib/OpenAPI/Client/OpenAI/Methods.pod` — Method documentation (includes links to examples)

These `.pod` files are generated artifacts — never edit them by hand. After
updating the spec, regenerate via `devel/rebuild` (see "Regenerating
documentation" above).

### Test Framework

Tests in `t/` use `t/lib/OpenAITests.pm`, a custom test base that imports common modules and provides `run_test_cases()` for declarative API testing. Most tests require a live `OPENAI_API_KEY` and internet access — they are skipped without it. Tests use `Test::Most` and `Test::RequiresInternet`.

Tests in `devel/t/` cover the doc generator, need no API key, and are
self-contained (each wires its own `lib` paths via `FindBin`). They run as part
of `make test`.

### Key Conventions

- API methods use **camelCase** names matching the OpenAPI operationId (e.g., `createChatCompletion`)
- A snake_case alias exists for every operationId; both spellings are supported
- Methods are called as: `$client->methodName({ body => { ... } })`
- Methods return a Mojo::Transaction; access response via `$tx->res->json`
- File uploads use the custom transactor: `$client->createTranscription({}, file_upload => { file => $filename, model => ... })`
- The `assistants => 1` constructor option adds the `OpenAI-Beta: assistants=v2` header
- `t/pod-coverage.t` runs `all_pod_coverage_ok` across all of `lib/`, so any new public sub in either module needs POD or `RELEASE_TESTING=1 make test` fails
